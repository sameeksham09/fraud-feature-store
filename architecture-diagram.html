Medallion Layers — Why 3 copies?
🥉

Bronze — Land Raw First

s3://features/bronze/ · JSON · append

Every raw Kafka message dumped unchanged. Like a security camera tape. If your transform logic was wrong, you don't lose data — you just replay the tape.

ELT  ·  IMMUTABLE  ·  AUDIT
🥈

Silver — Clean & Curated

s3://features/windowed_features/ · Parquet · append

Windowed aggregates computed by Spark. Columnar, compressed. Feast reads this for historical training. This is what the model learns from.

ETL  ·  PARQUET  ·  FEAST OFFLINE
🥇

Gold — Ready to Serve

Redis · Hash · user_features:* · 24h TTL

Latest value per user, in memory. API reads this directly (no Feast) for <10 ms lookups. Always fresh — written every 30s.

ETL  ·  REDIS  ·  LIVE SERVING
🎯

Hybrid ELT + ETL

Bronze is ELT (Extract-Load-then-Transform: land raw first, transform later). Silver + Gold are ETL (Extract-Transform-then-Load). Interview line: "Feast is intentionally not on the live path to avoid materialization lag."

Follow One Transaction — user_0001 buys $2,500 laptop in NG
1

Producer emits JSON onto Kafka

{"transaction_id":"txn_abc123","user_id":"user_0001","amount":2500,"merchant_category":"electronics","merchant_country":"NG","timestamp":"2026-09-05T14:05:00"}

2

Spark reads & parses the stream

Parses bytes → typed columns → adds event_time. Watermark 10 min handles late arrivals.

3

Spark computes windowed aggregates (last 5 min for user_0001)

Group by 5-min tumbling window + user. e.g. txn_count_5min=7, total=8200, avg=1171, max=2500. Also computes flags: is_foreign=1, is_high_amount=1, is_suspicious=1.

4

Dual writes in parallel (4 queries)

Q0 raw JSON → Bronze (S3). Q1 windowed aggregates → Redis user_features:user_0001 (HSET, TTL 24h). Q2 flags → Redis txn_flags:txn_abc123. Q3 aggregates → Silver Parquet.

5

FastAPI serves a prediction

Client: POST /score {"user_id":"user_0001","amount":2500,"merchant_category":"electronics","merchant_country":"NG"}
API: HGETALL user_features:user_0001 → builds feature vector in FEATURE_ORDER → model.predict_proba() → returns:

{
  "fraud_probability": 0.92,
  "risk_level": "HIGH",
  "features_used": [2500, 7, 8200, 1171, 2500, 1, 1, 1],
  "latency_ms": 8.4
}

6

Explainability (opt-in)

POST /score?explain=true or POST /explain adds: explainability: {shap_values, top_contributors[3], reasons[], method: "shap" | "importance_fallback"}. e.g. "High amount ($2500) · 7 transactions in 5 min · Suspicious country NG"

This order (FEATURE_ORDER in api/main.py & models/train.py) must match exactly. Feast schema + training columns + serving vector — all three must align or predictions are silently wrong.

⚠️

Common gotcha

Adding a new feature? Update all three: features.py (shared logic) → feast/features.py (schema) → models/train.py (retrain) → api/main.py (FEATURE_ORDER). Then retrain or the model will read columns shifted.
